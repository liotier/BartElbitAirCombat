# Increment 6 Specification — Review Record

Date: 2026-07-23. Reviewed: draft 1 of `increment-6-specification.md`. Result: revision 2 of the specification (same file), which this document justifies finding by finding.

This is an adversarial review in the spirit of the increment-1/3/4/5 reviews: the goal is to find what is *wrong* with the draft, especially defects that would let a correct implementation of the draft pass its own tests while the thing the increment exists to prove — that the c172x-shaped pipeline genuinely generalises to other airframes — is not actually achieved, or that would make a literal implementation of the draft fail at runtime. This increment's domain is JSBSim aircraft-config integration, so the review hunts for the kind of wrongness that domain is prone to: config assumptions that hold for c172x but silently don't for another airframe, and the interaction of an airframe swap with the prediction/reconciliation and wire-protocol machinery increments 4-5 built and only ever exercised against c172x.

## Method

As with every prior review, load-bearing claims were checked by building and running real code, not by reasoning alone. One probe (`probe_inc6_review.cpp`) was built for this review, exercising five things the draft asserts but never checked, against the real fetched JSBSim tree through `FlightSession`'s exact initialisation sequence: LoadModel case sensitivity, missing-property read behaviour, the full `sample()` property set per airframe, cross-airframe determinism, and whether increment 5's multiclient cross-talk thresholds transfer. Two of the review's own going-in hypotheses were *disproven* by running the probe (the `sample()`-throws worry and the cross-talk-thresholds-don't-transfer worry both turned out fine), and one defect the review did not anticipate (case sensitivity) was found only because the probe was actually run — the same pattern every prior increment's empirical validation has produced.

## Findings

Severity: **blocking** = a literal implementation of the draft fails at runtime, or a correct implementation could pass its own tests while a real defect ships; **major** = would send the implementer down a wrong path or leave the increment's central claim untested; **minor** = clarity/precision.

### B1 (blocking) — The catalog names Camel `camel`, but JSBSim's model is `Camel`; `LoadModel("camel")` fails at runtime on Linux

Draft 1's "Aircraft catalog" table lists the aircraft `name` as `c172x` / `camel` / `pa28` (all lowercase), and the `--aircraft {c172x|camel|pa28}` CLI and every prose reference use lowercase `camel`. The draft's implied `FlightSession::initialize(name)` passes that name straight to JSBSim's `LoadModel`. **Measured (`probe_inc6_review.cpp`, finding 0): `LoadModel("camel")` FAILS; `LoadModel("Camel")` succeeds.** JSBSim resolves the model name to `aircraft/<name>/<name>.xml` on a case-sensitive filesystem, and the directory is `Camel/Camel.xml`. The earlier pre-drafting validation (the spec's own Appendix B) happened to pass `"Camel"` and so never exposed this; the draft's *table* then wrote it lowercase for CLI tidiness, silently diverging from the string that actually loads. A literal implementation — `LoadModel(configuredAircraftName)` with the catalog as written — never loads Camel on the Linux target, failing exactly where the increment claims success.

This is the whole increment's failure mode in miniature: an assumption that held for c172x (whose directory *is* its lowercase name) silently not holding for another airframe.

**Resolution (revision 2)**: the catalog carries three explicitly-distinct fields per aircraft, never conflated — a user-facing/CLI/wire **token** (`c172x`/`camel`/`pa28`, lowercase, what `--aircraft` and the wire `aircraft_id` mean), the **exact JSBSim `LoadModel` string** (`c172x`/`Camel`/`pa28` — note the capital only on Camel), and the numeric `aircraft_id`. The spec now states that the LoadModel string is whatever JSBSim's directory is actually named, case included, and is not to be derived by lowercasing (or any other transform of) the token. pa28 and c172x happen to have token == model string; Camel does not, which is exactly why the two must be separate columns rather than one.

### M1 (major) — The test plan proves "flies without crashing," but never proves the prediction/reconciliation stack works for a non-c172x airframe — the increment's central claim

Draft 1's test 2 flies Camel and pa28 against a live server and checks "no NaN, no divergence, no crash." Its acceptance criterion 5 says the same. But the client every human uses (`PredictedAircraft`) *always* runs client-side prediction and reconciliation (increments 4-5) — there is no non-predicting client anymore. So "does the pipeline generalise" really means "does prediction+reconciliation, validated only against c172x in increment 4, still track tightly and reconcile cleanly for Camel and pa28." A client that mispredicts every tick and gets yanked back by a correction every single snapshot would *still pass* test 2's "no NaN / no crash / bounded" bar while delivering exactly the broken experience the increment is supposed to rule out. The draft's own "Open questions" even leans toward *not* giving `--mode prediction` an `--aircraft` flag — precisely the check that would catch this.

The good news, established by this review rather than assumed: **cross-airframe determinism is bit-identical** (`probe_inc6_review.cpp`, finding 3 — two independent instances of Camel, and of pa28, run through an identical 3-second mixed-input schedule, diverge by exactly `0.0` in latitude, altitude, roll and pitch, matching what c172x does). Determinism is the load-bearing premise under all of increment 4's prediction work, and it demonstrably generalises. That makes the fix cheap and removes the excuse for skipping it: `flight_test_client --mode prediction`'s tests 1/3/4 (immediate response, bounded-envelope tracking, forced-desync recovery) compare the predicting client against the *live server*, not against a pre-recorded c172x ground truth, so they are airframe-independent and can run for any type via `--skip-eventual-agreement` (only test 2, eventual-agreement, needs the c172x `server_pitch_response.csv` and is correctly skipped).

**Resolution (revision 2)**: `flight_test_client` gains `--aircraft`, and the test plan adds `--mode prediction --aircraft camel --skip-eventual-agreement` (and the pa28 equivalent) asserting the immediate-response, bounded-envelope, and forced-desync-recovery criteria — the automated proof that the prediction stack itself generalises, not merely that the aircraft doesn't explode. Acceptance criterion 5 is strengthened accordingly.

### M2 (major) — `ServerWelcome` gains a field, but the spec doesn't bump `kProtocolVersion`, and increment 6 is the first increment where that actually bites

Draft 1 adds `aircraft_id` to `ServerWelcome` and explicitly says every other message and `kProtocolVersion` are unchanged. But the version handshake exists precisely to reject a client and server built from *different* trees before they start exchanging misparsed messages — and this change breaks that guarantee without tripping it. Confirmed from the serialization code: `deserializeServerWelcome` reads its fields and returns without checking that the buffer was fully consumed, so a **new** client (expecting the 14-byte welcome) reading an **old** server's 13-byte welcome fails its final `getU8(aircraft_id)` and rejects the welcome as malformed — with no clean "version mismatch" signal — while an **old** client reading a **new** server silently ignores the trailing byte and can never see `aircraft_id` at all. Both build-skew directions are exactly what the version field is for.

This has been a latent gap since increment 4 (increments 4 and 5 both changed `AircraftState`/`StateSnapshot`/`ServerWelcome` layout while leaving `kProtocolVersion` at 1), and prior reviews — including mine of increment 5 — missed it. What makes it worth fixing *now* rather than noting as pre-existing: increment 6 is the first increment whose entire point is people running a server that others connect to from *their own separately-built binaries* (the `build_server.sh`/`build_client.sh` split shipped last session, the `--aircraft`/`SERVER_HOST` operator/player coordination this increment adds). Independent builds with skewed wire formats stop being a CI-only abstraction and become a realistic tester setup.

**Resolution (revision 2)**: bump `kProtocolVersion` to 2, and state as a standing rule that any change to a message's wire layout bumps it — with a one-line acknowledgement that increments 4-5's layout changes should have and didn't, so the bump to 2 covers the accumulated drift, not only `aircraft_id`.

### M3 (major) — "Prints a warning" under-specifies what a mismatched client actually does, and determinism makes the stakes concrete

Draft 1 handles a client configured for one aircraft connecting to a server running another by comparing `ServerWelcome.aircraft_id` against the locally-loaded type and printing "a loud, specific warning," then — implicitly — continuing to fly. With determinism now confirmed (M1), the consequence is no longer vague: a mismatched client predicts a *different airframe's* physics from the server's authoritative state and is therefore corrected, hard, on essentially every snapshot — not a subtle degradation but a continuously-fighting, unplayable session that nonetheless satisfies "no crash." The draft dismisses the obvious alternative — have the client trim the server's *announced* aircraft instead of a pre-configured one — in a single clause ("more invasive... a real behavioural change to an already-working sequence") without weighing it.

The dismissal is defensible but the draft doesn't earn it. `PredictedAircraft::_ready()` currently trims *before* connecting; adopting the server's type means deferring the trim until `ServerWelcome` arrives, which is more than a one-line change and does touch an already-validated sequence. Against that, warn-and-fly-wrong is the same "coordinate it out of band, like `--port`" contract the rest of the client already uses. Either choice is legitimate; shipping the spec without explicitly making one, and without stating the mismatch *behaviour* precisely, is not.

**Resolution (revision 2)**: the spec now (a) states the mismatch behaviour explicitly and precisely — warn loudly, name both configured and announced types, and **keep flying only if a deliberate override flag is set; otherwise disconnect rather than present an unplayable continuously-corrected session** — and (b) records the adopt-the-server's-type alternative as a named, deferred option with the concrete reason (deferring trim past `_ready()` is a real change to the increment-4 sequence, out of scope for a derisking increment whose out-of-band coordination story matches `--port`), so a future increment can revisit it deliberately rather than rediscover it.

### m1 (minor) — Scripted mode plus a non-c172x `--aircraft` is left undefined

The draft says scripted mode (`flight_server --scenario pitch_response`, increment 1's regression scenarios) "stays c172x-only and untouched," but never says what `--aircraft camel --scenario pitch_response` *does* — silently run Camel through c172x-tuned pass thresholds (which would spuriously fail or pass), or reject the combination. **Resolution**: the spec states that `--scenario` implies and requires c172x, and a non-c172x `--aircraft` combined with `--scenario` is rejected at startup with a clear message, rather than run.

### m2 (minor) — pa28's whole-server origin altitude deserves one confirming line

pa28's only validated trim point is ~1000 ft (Appendix B; 2000 ft and 5000 ft do not converge), so a pa28 server trims its shared origin and spawns every aircraft at ~305 m above the flat ground plane. That is fine — comfortably clear — but the draft sets the catalog altitude without noting that the shared-origin/spawn logic (increment 5) inherits it, leaving a reader to wonder whether 1000 ft was chosen with that in mind. **Resolution**: one sentence in "Aircraft catalog" noting the canonical altitude is also the shared-origin spawn altitude, and 305 m clears the ground plane with margin.

## Verified as sound (no change), grounded by this review's probe

- **`FlightSession::sample()` is airframe-safe.** Two going-in worries — that `sample()`'s c172x-shaped property set (e.g. `fcs/pitch-trim-cmd-norm`) might throw for an airframe whose FCS lacks a property, crashing the wholesale per-tick read — were both disproven: a direct `GetPropertyValue` on a deliberately-nonexistent property returns `0.0` quietly rather than throwing (finding 1), and the complete `sample()` set plus the three body-rate properties the networked path reads all resolve cleanly for c172x, Camel, and pa28 (finding 2). The airframe-independence of the state-sampling path holds — worth stating that it holds *because* JSBSim returns 0 for absent properties, not because all three airframes define an identical property set.
- **Cross-talk thresholds transfer.** The worry that increment 5's multiclient cross-talk gate (throttle 1.0, elevator ±0.8, needs ≥5 m altitude delta within 4 s) was c172x-calibrated and would spuriously fail for a lower-powered airframe was disproven: all six cases pass (finding 4). Noted residual, not a blocker: the *magnitudes* vary a lot (c172x climbs +80 m by 4 s, Camel only +23 m), and Camel's nose-up climb visibly *plateaus/reverses* between 3 s and 4 s (+23.8 → +23.1 m — energy bleed near stall at 65 kt with full-aft elevator). The 5 m gate clears with ~18 m of margin so the automated test is safe, but Camel's plateau is a real "feel" flag for the human-verification criterion, and a reminder that the test's loose threshold is doing real work here.
- **No stray output files for the new airframes.** c172x writes `JSBout172B.csv` during `LoadModel` (gitignored). Checked directly: Camel's file-output block is commented out in its config and pa28 has none — their only `<output>` tags are FCS property assignments, not file writers — so `DisableOutput()` plus these configs produce no new stray files and need no new `.gitignore` entries.
- **The wire change is additive and correctly minimal.** A single trailing `uint8 aircraft_id` on `ServerWelcome` only; no other message touched, consistent with the airframe being orthogonal to the physical-state fields every snapshot already carries. (The versioning consequence is M2; the field itself is right.)

## Implementation model recommendation

**Recommendation: Sonnet, in a session that can build and run**, matching every prior increment. None of the findings is an open research question: B1 is a catalog-structure fix, M1's premise (determinism) is now measured and its check reuses existing prediction-mode machinery, M2 is a one-line version bump plus a rule, M3 is a design decision this review has now made explicit, and m1/m2 are clarity. Escalate to a frontier model only if implementation surfaces a *further* airframe-specific interaction the corrected spec doesn't cover — not anticipated, given the three-airframe fleet is now validated for load, trim, determinism, state-sampling, and control response.

## Residual risks

1. **Camel's energy state under sustained full-aft elevator** (the plateau/reversal in finding 4) is a low-speed-airframe reality, not a bug, but it means Camel is the airframe most likely to look or feel marginal in the human-verification check — flagged there, not solved here.
2. **pa28's single validated trim point** (~1000 ft) is unchanged from pre-drafting; a future need for pa28 at altitude would require re-validating its trim envelope, exactly as this increment declined to.
3. **The human "does Camel/pa28 fly right" judgement** (acceptance criterion 8) remains genuinely out of reach of the automated suite, as with every rendering/feel criterion since increment 4; the automated additions from M1 prove the *pipeline* generalises, not that a WWI biplane feels good to fly.
4. **Real Spitfire/Bf-109** remain YASim-only and out of scope, unchanged; the fleet proves generalisation across three JSBSim airframes of genuinely different eras and handling, which is what the increment set out to derisk.
