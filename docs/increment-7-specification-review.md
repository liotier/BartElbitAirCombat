# Increment 7 Specification — Review Record

Date: 2026-07-23. Reviewed: draft 1 of `increment-7-specification.md`. Result: revision 2 of the specification (same file), plus one genuine architecture decision surfaced for the project owner (finding B1's resolution fork).

This is an adversarial review in the spirit of the increment-1/3/4/5/6 reviews: find what is *wrong* with the draft, especially defects that would let a correct implementation of the draft's *machinery* pass its own tests while the thing the increment exists to produce — bots that actually stay in the air and look sane — is not achieved. The draft's process/lifecycle half (fork/exec/signal/reap) was validated before drafting (its Appendix B) and holds up. This review therefore concentrated on the half the draft did *not* probe: the flight behaviour of a client that, by explicit design, has no local physics.

**Resolution recorded (post-review, project owner):** finding B1's architecture fork was resolved toward **giving the bot a real local `FlightSession`** — not merely as the fix for keeping aircraft airborne, but because the later air-combat increment's bot smarts require the bot to apply its own flight-dynamics model to manage energy (fuzzed by a per-bot handicap factor), which a physics-less bot could never do. That decision, plus the owner's capacity/CPU-leveling model, non-human wire marking, and remote-bot direction, are folded into specification **revision 3**. Notably, the local-physics choice *removes* revision 2's server-seeded-trim wire change and its protocol-version bump (the bot now knows its own trim), leaving this increment with no wire-layout change at all. The findings below stand as the analysis that led there; where revision 3 supersedes a resolution, it is noted inline.

## Method

Load-bearing claims were checked by building and running real code. Three probes (`probe_inc7_bot.cpp`, `_bot2.cpp`, `_bot3.cpp`) replicated the server's *exact* per-tick command application (`src/server/main.cpp`'s `applyClientCommand`: set `elevator/aileron/rudder/throttle-cmd-norm` each tick from the client's command, leaving the trim's `pitch-trim-cmd-norm` untouched) and drove a real `FlightSession` for each of increment 6's three airframes (c172x, Camel, pa28) under a bot's control schedule for 90 simulated seconds — three full maneuver cycles — flagging departure (NaN, ground contact, spiral past 80° bank, or stall below 20 kt). Four control styles were tested, from what a trim-blind physics-less bot can do up to a stabilised, coordinated, closed-loop controller. The results reshaped the review's central finding from a suspected clarity gap into a blocking one.

## Findings

Severity: **blocking** = a correct implementation of the draft could pass its process/wire tests while the bots do not actually stay airborne (the increment's whole point), or the draft asserts a mechanism that measurably does not work; **major** = a real defect or wrong path left unaddressed; **minor** = clarity/precision.

### B1 (blocking) — The "simple, deterministic, time-based" maneuver over a physics-less bot keeps *no* airframe airborne; keeping aircraft flying is a closed-loop, trim-dependent, airframe-sensitive control problem the draft under-specifies to the point of non-function

Draft 1's Architecture describes the bot as having **no local physics** ("depending only on `netcore` and `interpcore` — critically, **not** `flightcore`/JSBSim") and its maneuver logic as "a simple, deterministic, time-based repeating pattern... sent as `ControlInput`," with "a soft bias back toward the aircraft's own trimmed level-flight attitude" as a safety net. Measured, this does not work, in three compounding ways:

**(1) A physics-less bot cannot self-determine trim, and losing trim departs every airframe.** JSBSim's trim writes non-zero solutions into `aileron-cmd-norm` and `rudder-cmd-norm` (measured: c172x aileron −0.075 / rudder −0.004; **Camel aileron +0.102 / rudder −0.064**; each airframe different), and the trimmed throttle differs sharply (c172x 0.792, Camel 0.301). The server *overwrites* all of these every tick with the client's command. A bot that cannot compute trim — which a physics-less bot cannot — sends aileron/rudder = 0 and a guessed throttle, discarding the airframe's roll/yaw/thrust trim. Measured (`probe_inc7_bot.cpp`): a trim-blind bot **departed all three airframes** (c172x and Camel spiralled past 80° bank, pa28 flew into the ground). This is the increment-4 "you must reproduce every non-zero trimmed axis" finding resurfacing for a client that *structurally cannot* reproduce them. (Pitch is the one exception: the trim's pitch solution lives in `pitch-trim-cmd-norm`, which the server does not overwrite, so elevator commands *around zero* are automatically around trim — which is why the fix below is about the other three axes.)

**(2) Even trim-aware, an open-loop deflection schedule is the wrong control model.** Aileron commands roll *rate*, not roll *angle*, so any sustained net aileron integrates bank without bound — a "hold aileron for the turn phase" schedule barrels into a spiral rather than settling into a shallow turn. Measured (`probe_inc7_bot2.cpp`): a trim-aware bot given even a *gentle* fixed aileron delta still departed the Camel, because the bank never rolls back out. A stable shallow turn is inherently a closed-loop attitude-hold task (roll in to a target bank, neutralise, hold, roll out), which needs the aircraft's *current* attitude as feedback — the exact thing the draft treats as an optional "soft bias" rather than the load-bearing mechanism.

**(3) The control problem is airframe-sensitive, and the Camel is materially harder than the GA types.** A stabilised, coordinated controller — proportional on bank error, derivative (roll-rate) damping, rudder turn-coordination, trim-aware, holding a 15° shallow turn (`probe_inc7_bot3.cpp`) — flew **c172x and pa28 rock-solid** (bank held at 16° and 13°, altitude within ~50 m over 90 s) but **still spiralled the Camel** (bank 81°, speed bled from 65 kt to 35 kt). This does not prove the Camel unflyable — a per-airframe-tuned autopilot with roll-rate damping and speed protection very likely can fly it — but it does prove that a *single, simple, airframe-blind* controller does not, and that a low-power, low-speed, spiral-prone WWI biplane trimmed near its own energy margin (recall increment 6's finding that Camel's climb plateaus near stall) is a genuinely harder control target than the draft's "doesn't need to be fancy" implies.

Taken together: a literal implementation of the draft — physics-less bot, time-based deflection schedule, no server-supplied trim — produces bots that spiral or sink within the first maneuver cycle, failing the increment's own acceptance criterion 5 ("genuinely evolving... not glitchy, spinning, or frozen"; note that an aircraft evolving straight into a spiral technically satisfies "not frozen") and the user's explicit "capable of remaining airborne" requirement. The process/wire machinery would pass its tests while the bots fall out of the sky.

**Resolution (revision 2)** — the minimal set that makes a physics-less bot viable, all folded into the spec:

- **The server seeds each bot its trimmed control vector** (`aileron`, `rudder`, `throttle`; elevator baseline is already handled by `pitch-trim-cmd-norm`). The server trims every aircraft anyway, so it *has* these values; the bot cannot compute them, so it must be told. This is a **wire change** (contradicting draft 1's "Wire protocol changes: None") — the cleanest carrier is extending `ServerWelcome` (already gaining `aircraft_id` in increment 6) with the three trim floats, or a small dedicated post-welcome `TrimBaseline` message. Per increment 6's newly-adopted rule, this **bumps `kProtocolVersion` again** (to 3).
- **The maneuver logic is a closed-loop attitude controller**, not an open-loop schedule: hold a target bank for the turn phase (roll-rate-damped, rudder-coordinated) and target level between, target a gentle pitch for climb/descend — reading the bot's own current attitude and body rates each tick. The "time-based pattern" becomes a schedule of *attitude targets*, not *control deflections*.
- **The bot reads its own state for control from the latest *raw* received `AircraftState`, not the `RemoteEntityTracker`.** The tracker deliberately renders 100 ms in the past (`kInterpolationDelayS`) and extrapolates — correct for smoothing *other* aircraft for display, wrong as feedback for a control loop, which wants the freshest real datum. The tracker is still fed every entry for the "full airspace picture" of *others* (the forward-looking rationale is intact); own-state control just doesn't read back through it.
- **An automated airborne-endurance gate** replaces "flies a genuinely evolving pattern" as the real acceptance test: each airframe the bot fleet will fly must be shown to stay airborne (no ground contact, no spiral, no stall) for ≥ a few minutes of continuous unsupervised maneuvering, in a headless server-side harness, *before* the human "looks sane" check. Acceptance criterion 5 is rewritten around this.
- **The Camel is gated on that endurance test, not assumed.** If a conservatively-tuned controller cannot keep the Camel airborne, the first bot implementation targets the GA airframes (c172x, pa28) and Camel is explicitly deferred from the bot fleet with the reason recorded — the same "shelve the hard airframe, revisit post-demo" discipline increment 6 applied to p51d/dr1/L17.

**The genuine fork this exposes (owner's decision, flagged not silently taken):** giving the bot **a real local `FlightSession`** — making it a true "headless human client" running its own `PredictedSession` exactly like the Godot client — *dissolves* (1), (2)'s feedback-latency issue, and the M2 framing problem below all at once: the bot would know its own trim (no seeding, no wire change), fly closed-loop against zero-latency local state, and exercise the full prediction/reconciliation path as a real test client. The cost is a per-bot trim (~12 ms) on spawn plus local physics stepping (the server already steps that aircraft, so it is stepped twice), against the draft's "populate the airspace cheaply" goal. Revision 2 is written to the **physics-less-plus-fixes** design (it preserves the draft's stated architecture and the "cheap" goal), with the local-physics alternative recorded as the primary open question — see the closing note and the spec's "Open questions."

### M1 (major) — The despawn-then-onboard sequence races the player_id free, which happens on ENet *disconnect*, not on `SIGTERM`

Draft 1: "the server despawns one bot **first** — freeing its player_id... — then proceeds with the human's normal onboarding." But "despawn" is defined as sending the bot's process `SIGTERM`, and a bot's player_id is actually freed by increment 5's existing path *when its ENet `DISCONNECT` event is processed* — which arrives some round-trips *after* the `SIGTERM`, not synchronously with it. Between the two, the slot is still marked in use (`playerIdInUse`, increment 5). If the human's onboarding tries to allocate a player_id in that window, it finds no free slot despite a bot having been "despawned," and either spuriously rejects the human or races the bookkeeping. The "first... then" phrasing hides a genuine asynchronous ordering problem.

**Resolution (revision 2)**: state explicitly that a displacing human's onboarding is sequenced *after* the despawned bot's `DISCONNECT` has actually been processed and its slot freed (the server initiates the `SIGTERM`, and completes the human's slot allocation only once the freed player_id is observed), or that a slot is explicitly reserved across the handoff. The mechanism must be named, not left as "first, then."

### M2 (major) — "A headless version of the human client" oversells a bot that has no prediction, weakening its stated value as a test client

Draft 1's Goal calls `flight_bot` "a simple, headless version of the networked client." But the networked client's *defining* feature is client-side prediction and reconciliation over a local `FlightSession` (increments 4-5); the bot explicitly has none. So it is not a headless *human client* — it is a headless *input source and observer*. This matters concretely because "useful... for automated testing" is one of the two stated purposes: a bot with no prediction exercises the server's multi-client acceptance/stepping/broadcast path (real value) but exercises the client-side prediction/reconciliation path **not at all** — so it is a weaker test client than the framing implies, and `flight_test_client --mode prediction` (increments 4/6) remains the only thing testing that path.

**Resolution (revision 2)**: the Goal is reworded to describe the bot as a headless *control-and-perception* client (sends `ControlInput`, receives the full snapshot picture) rather than a headless *human* client, and the test-client value is stated precisely (exercises server multi-client handling; does not exercise client prediction). This finding is also one arm of B1's fork — the local-physics design would make "headless human client" literally true and is noted there.

### m1 (minor) — Only *clean* shutdown was validated; a `flight_server` crash orphans its bots

Appendix B validated that `SIGTERM` to `flight_server` reaps its children — but a *crash* (`SIGKILL`, segfault) does not run that path, and POSIX does not kill children with their parent. Orphaned `flight_bot` processes would be reparented to init and keep running, connected to a now-dead port. **Resolution**: `flight_bot` exits on loss of its server connection (an ENet disconnect/timeout) — which also cleanly handles the "server restarted" case — and, on Linux, the implementer may additionally set `prctl(PR_SET_PDEATHSIG, SIGTERM)` in the child after `fork()` for defence in depth. Added as a spec bullet and an acceptance-criterion note, since "no orphaned processes" should hold under crash, not only under clean exit.

### m2 (minor) — The `bots_active = max(0, N − humans)` invariant is asserted as if instantaneous; it is eventually-consistent

Spawn (fork + connect + async server-side onboard, increment 5's ~12 ms trim) and despawn (SIGTERM + async disconnect) both span many ticks, so the invariant cannot hold instantaneously and two near-simultaneous human connects, or a human connecting while a refill bot is mid-onboard, will transiently violate it. **Resolution**: state that the target count is re-evaluated and corrected on each *actual* ENet connect/disconnect event (idempotent, event-driven), converging to `N` rather than holding it every instant — and that a mid-flight refill bot counts toward the target the moment it is `fork()`ed (not only once welcomed), so a burst of connects cannot over-spawn.

### m3 (minor) — Startup spawns N bots with no pacing named

`--bots N` at startup `fork()`s N processes that connect and trigger N concurrent server-side async trims. Increment 5 validated concurrent construction but at a bounded scale; a large `N` is an unpaced connection-and-trim burst. **Resolution**: one line noting bots are spawned within the existing `--max-clients` bound (so N is already capped at a modest number) and, if a future large fleet is wanted, spawned paced across a few ticks rather than all in one — not load-bearing at the intended scale, but worth stating the bound.

## Verified as sound (no change)

- **The fork/exec/SIGTERM/waitpid/no-zombie process lifecycle** (Appendix B) — re-read and re-confirmed; the child-spawn, liveness-check, clean-signal-disconnect, reap, and no-zombie results are solid and correctly grounded, and remain the right mechanism. B1 does not dispute any of this — it disputes what the spawned process *does in the air*, not that it spawns and dies cleanly.
- **"Indistinguishable on the wire from a human client"** for the *existing* messages — true and desirable; the bot's `ClientHello`/`ControlInput`/`StateSnapshot`/`PlayerLeft` are byte-identical. (B1's trim-seed adds a *new* server→client field/message; it does not make the bot's *own* traffic distinguishable.)
- **Sharing the real player_id/capacity pool** (vs `--stress-aircraft`'s separate range) — the right call for "a bot occupies a slot a human could take"; M1 refines *how* the handoff is sequenced, not *whether* the pool is shared.

## Implementation model recommendation

**Recommendation: Sonnet, in a session that can build and run — but only after the owner resolves B1's fork** (physics-less-plus-fixes vs local-physics bot), because that choice changes what is built. If physics-less: the closed-loop controller and its per-airframe endurance tuning are the real work and should be developed against the same headless `FlightSession` harness this review used, *before* wiring the network path, so controller tuning is not entangled with ENet timing. If local-physics: much of increments 4-5's `PredictedSession` is reused and the control loop runs against zero-latency local state, but the bot binary grows a `flightcore`/JSBSim dependency and a per-bot trim cost. Either way the endurance gate (B1) is the acceptance test that matters.

## Residual risks

1. **Controller tuning is airframe-specific and, for the Camel, not yet shown achievable** — the review proved the *problem* is real and the GA types are easy; it did not produce a Camel-flying controller. Whether the Camel joins the bot fleet is gated on the endurance test, not assumed.
2. **The human "do bots look sane" check** (acceptance criterion 8) remains subjective and out of the automated suite's reach, as with every prior increment's feel criterion — but is now backed by a hard automated airborne-endurance pre-condition, so a human is never asked to judge an aircraft that is quietly spiralling.
3. **The local-physics fork, if taken, reopens the "double physics" question** (server and bot both step the same aircraft) — not a correctness problem (they are deterministic and the server remains authoritative) but a cost one, worth measuring if bot counts grow.
