# Increment 5 Specification — Review Record

Date: 2026-07-23. Reviewed: draft 1 of `increment-5-specification.md`. Result: revision 2 of the specification (same file), which this document justifies finding by finding.

This is an adversarial review in the spirit of the increment-1/3/4 reviews: the goal is to find what is *wrong* with the draft, especially defects that would let a correct implementation pass its own tests while the thing the increment exists to prove is not achieved. This increment's domain spans two of the categories the roadmap names for review focus — "real-time-architecture and threading judgment" (increment 2's domain, now returning at real multi-core scale) and "netcode-specific failure modes" (the networking increments' domain) — so this review hunts for both: concurrency bugs the draft's own probes don't actually cover, and wire-protocol/reconciliation interactions that chunking and multiple clients newly introduce.

## Method

As with every prior review, load-bearing claims were checked by building and running real code, not by reasoning alone. One new probe was built specifically for this review (`probe_dynamic_pool.cpp`) to close a gap the draft's own pre-drafting probes left open; its result is folded into the revised spec as a passed gate, the same way increment 4's review passed the reconstruction gate before implementation.

## Findings

Severity: **blocking** = a correct implementation of the draft could pass its own tests while a real defect ships, or the draft asserts something demonstrably false that the design rests on; **major** = would send the implementer down a wrong path or leave a real risk untested; **minor** = clarity/precision.

### B1 (blocking) — The validated barrier pattern doesn't cover what the server actually needs, and taken literally, produces a design that cannot handle a changing aircraft count

Draft 1's "Per-tick barrier" bullet says the barrier is "the same class and usage pattern validated in `probe_multithread2.cpp`, ported with no change beyond being reused across the server's whole lifetime instead of one fixed-length benchmark run." **This is not true, and the difference matters.** `probe_multithread2.cpp` validated exactly one thing: T worker threads, each with a `[lo,hi)` chunk captured *once* in its thread-creation lambda, stepping a *fixed* N aircraft in lockstep with each other via a T-party (workers-only) barrier, for the length of one benchmark run. Main never participated in that barrier and never mutated shared state mid-run — the probe's own structure (workers loop internally; main just `join()`s at the very end) has no between-tick phase for main to do anything in at all.

The real server needs something the probe never exercised: a new client's aircraft must be spliced into the active list *while the worker pool is already running*, and each worker's chunk boundary must therefore be recomputed from the *current* aircraft count every tick — not captured once at thread-creation time, when the count could still be 1. Taken at face value, the draft's architecture section gives an implementer nothing to do this with: a literal port of the validated pattern hard-codes `[lo,hi)` per worker for the pool's entire lifetime, meaning a second client connecting after the first tick has already run would either be silently never stepped, or crash on an out-of-bounds `sessions[i]` access the moment the implementer tries to make the chunk boundaries follow a growing vector. Acceptance criterion 3 ("a new connection arriving while other aircraft are actively flying") would force an implementer to discover this gap while writing the code — but the spec's job, per this project's own standing process, is to pin the mechanism down explicitly, not leave the implementer to invent one under time pressure (a plausible bad fix: destroy and recreate the whole worker pool on every roster change, which is correct but reintroduces per-connection thread-creation cost and could itself cause the very tick-time spike criterion 3 is trying to rule out).

There is a second, related gap the draft never addresses: **where does per-client `ControlInput` command-buffer bookkeeping happen relative to ENet polling and the stepping phase?** Today's single-threaded server mutates `pendingCommands`/`nextExpectedSeq` from the `onEvent` callback (driven by `server.poll()`, on the one and only thread) and reads/applies them immediately before `step()`, on that same thread — no race is possible because there is only one thread. The draft's multi-core design doesn't say whether command-buffer lookup+apply happens serially on main before dispatch, or per-worker immediately before each aircraft's `step()` (parallelism-favors the latter), and doesn't state *when* `server.poll()` is allowed to run relative to the worker pool being active. Without an explicit rule, an implementer could plausibly call `server.poll()` at some point while workers are already mid-tick (e.g. "poll a little between building each snapshot chunk to stay responsive") — which would be a genuine, hard-to-reproduce data race between main's `onEvent`-driven writes to a client's command buffer and a worker's concurrent read of that same buffer.

**Fix, verified this review** (`probe_dynamic_pool.cpp`, gate passed — see the addendum below): a single `SpinBarrier` sized `T+1` (workers **and** main), called via `arriveAndWait()` exactly once per tick by every party, with a strict discipline:
- **Main's shared-state mutations** (splicing the aircraft list, updating the published aircraft count, and — by the same logic — draining `server.poll()` and updating per-client command buffers) happen only in main's code *between* two consecutive `arriveAndWait()` calls, and are complete *before* main makes its next call.
- **Workers read that state only *after* their own `arriveAndWait()` call returns**, recomputing their own `[lo,hi)` chunk boundary fresh from the current aircraft count *every tick* — never caching it across ticks — and popping/applying their own assigned aircraft's next queued command immediately before stepping it (parallelism-friendly, and safe because main's `onEvent`-driven mutation of that same buffer is guaranteed already finished by the barrier).

This is the standard bulk-synchronous-parallel ("superstep") pattern — one barrier call per round, mutate-before-call on the producer side, read-after-return on the consumer side, with the barrier itself providing the only happens-before edge needed in both directions. It requires no new dependency (still the same hand-rolled `SpinBarrier` class) and no additional synchronization primitive; it is a correction to which *pattern of use* the draft prescribes, not a new mechanism. `probe_dynamic_pool.cpp` implements exactly this and confirms it: a run that adds 15 aircraft at tick 100 and removes 8 at tick 250, across T=1–4, produces the exact expected per-worker tick count every time (400/800/1200/1600 for T=1/2/3/4) and zero divergence among aircraft that flew an identical number of ticks. (An initial version of this same check compared *all* surviving aircraft against each other regardless of when they joined, and found a spurious 8.5×10⁻⁴ "divergence" — identical in magnitude at T=1, where no race is even physically possible, which is what immediately flagged it as a test-methodology bug rather than a real one: aircraft that joined 100 ticks late are legitimately not at the same simulated state as aircraft present from tick 0, and comparing across that boundary is comparing the wrong things, the same category of self-caught artifact this increment's pre-drafting validation already produced twice.)

The revised spec's "Server-side concurrency" section is rewritten to specify this protocol explicitly rather than gesture at reusing the probe.

### M1 (major) — Reconciliation's trigger condition under chunking needs to be pinned down, or an implementer could reintroduce the wait-for-complete-snapshot dependency chunking exists to avoid

Draft 1's "Wire protocol changes" point 2 says a client processes each chunk independently as it arrives, and that the aircraft in a lost chunk simply keep last tick's state. This is correct as far as it goes, but the draft never states, for the reading client's *own* aircraft specifically, exactly when reconciliation (`predictcore::PredictedSession::reconcile()`) should be invoked. Left unstated, there are two plausible-but-wrong readings: (a) trigger reconciliation once per received *snapshot tick* (i.e. try to detect "all chunks for this tick have arrived" first) — this silently reintroduces the reassembly-completeness dependency chunking was specifically designed to avoid, and would leave the client's own aircraft's reconciliation stalled behind an unrelated chunk carrying only *other* aircraft; or (b) invoke it on every received chunk regardless of content — harmless (a no-op check) but wasteful and easy to get subtly wrong if the "is my own entry in this chunk" check is fumbled.

**Resolution**: state explicitly, as a normative rule, that reconciliation triggers exactly when the chunk *containing the reading client's own `player_id`* arrives — independent of whether sibling chunks for the same `server_tick` have arrived, are still in flight, or were dropped. This is a direct consequence of "each client's own record is never split across chunks" (already true, since chunking only splits the *list* of aircraft, never a single aircraft's fields) and needs one sentence to make watertight rather than left implicit.

### M2 (major) — The test plan's `--stress-aircraft` flag doesn't specify a `player_id` allocation range, and as illustrated risks colliding with real clients' pool

Test-plan item 7 proposes `--stress-aircraft 30` alongside "a few real connected clients" to cross the 16-aircraft chunk boundary, and separately, item 6 tests `kServerFull` with a small `--max-clients`. Draft 1 never states whether synthetic stress aircraft draw `player_id`s from the *same* `[1, maxClients]` pool real clients use, or a separate range. If they share the pool, `--stress-aircraft 30` would require `--max-clients` set to at least 30 just to have room — quietly conflating "how many real clients may connect" with "how many total aircraft exist for chunking purposes," and potentially causing test 7 to either fail to start (if run with a small, test-6-style `--max-clients`) or to silently test a different `maxClients` value than test 6 exercises, muddying what each test actually proves.

**Resolution**: synthetic stress aircraft draw `player_id`s from a range above `maxClients` (e.g. starting at 200, since `player_id` is a `uint8` with 255 as the practical ceiling — comfortably above any `maxClients` this project would plausibly configure) and are never counted against the real-client capacity check. This is a one-sentence fix but a necessary one — without it, test 7 as literally described doesn't obviously run at all under test 6's own `--max-clients` example.

### m1 (minor) — The test plan should name chunk-boundary edge cases explicitly

Item 7 tests "comfortably crossing" the 16-aircraft boundary but never asks for a count *at* the boundary. Off-by-one errors in a `ceil(N/kMaxAircraftPerChunk)` computation or a chunk-loop bound are exactly the kind of defect boundary values catch and a merely-comfortable count would miss. Add explicit counts of 16 (exactly one full chunk), 17 (one chunk plus a single straggler), and 32 (exactly two full chunks) alongside the "comfortably above" case.

### m2 (minor) — `interpcore`'s single-sample case (a brand-new remote entity) should be named as already handled, not left for the implementer to wonder about

A newly-appeared `player_id`'s tracker entry starts with exactly one buffered sample — no bracketing pair exists yet for interpolation. Draft 1 doesn't say what happens here, which could read as a missing case needing special-casing. It doesn't: the existing extrapolation path (dead-reckon forward from "the last known sample") already degrades correctly to this case, since a single sample *is* "the last known sample," and `render_time` (which is always `now - 100ms`, and therefore always at or after the first moment a real sample could exist) naturally falls on or after it. Worth one sentence stating this explicitly so an implementer doesn't write a redundant branch.

## Verified as sound (no change)

- **The standalone step-cost re-measurement and the roadmap's superseded ~254/57.2 µs figures** — re-confirmed by this review's own re-reading of Appendix B; the correction is real and well-supported.
- **4-thread lockstep stepping being safe** (the *sub-piece* `probe_multithread2.cpp` actually tested — T workers in lockstep with *each other*, fixed N) — this remains true and is not what B1 disputes; B1 is about what happens *around* that validated core, not the core itself.
- **Concurrent construction, and the mixed step+onboarding case** — both hold up, including the self-caught measurement artifact in the mixed case, which this review re-derived independently while checking the draft's Appendix B narrative and found to be correctly reasoned.
- **The MTU/fragmentation finding** — re-derived independently from `enet-src/include/enet/protocol.h`'s struct sizes during this review (`ENetProtocolHeader` 4 bytes, `ENetProtocolCommandHeader` 4 bytes, `ENetProtocolSendFragment` 24 bytes, giving the same 1364-byte threshold the draft states) and cross-checked against the draft's own probe output table — arithmetic and observation agree, and the chunking response is the right, minimal fix rather than reaching for interest management prematurely.
- **The per-aircraft `ack_client_seq` relocation** — correctly reasoned; wire-size-neutral at N=1, and the only sensible design once a broadcast serves more than one client.
- **The choice of `kMaxAircraftPerChunk=16`** — comfortably under the tightened 23-aircraft threshold with real margin for future field growth.

## Implementation model recommendation

**Recommendation: Sonnet, in a session that can build and run**, matching every prior increment, *after* the B1 fix is folded in and re-validated (already done this review — `probe_dynamic_pool.cpp`'s gate is passed, so implementation does not need to re-derive the protocol, only follow it). The remaining findings (M1, M2, m1, m2) are clarity/completeness fixes, not open research questions. Escalate to a frontier model only if implementation surfaces a *further* concurrency subtlety the corrected protocol doesn't cleanly cover (e.g. if a future increment needs workers to communicate with each other mid-tick, not just with main) — not anticipated here, but the same standard the increment-4 review applied to its own M2 gate.

## Residual risks

1. **Sub-linear scaling headroom is measured on this session's 4-core sandbox.** The architecture adapts to whatever `hardware_concurrency()` reports, but a real deployment box's core count, and its specific scaling curve, could differ; not a design risk, but worth a real re-measurement once this runs somewhere other than this container.
2. **The c172x-vs-WWII-fighter cost question** (already named in the draft's own Appendix B) remains open until increment 6 actually swaps the aircraft model — flagged, not solved, here or there.
3. **Interpolation/extrapolation "feel"** is, like increment 4's blend feel, inherently subjective; the automated suite (per the test plan) proves tracking correctness and boundedness, not that it looks smooth to a human. No manual acceptance criterion is currently listed for this in the draft the way increment 4 had one for its own blend — worth adding a manual "watch two other aircraft fly smoothly" check to acceptance criteria during revision, given this project's established precedent of not treating automated correctness as a substitute for a human "does it feel right" judgment on anything rendering-facing.
4. **`--stress-aircraft`'s synthetic aircraft are unpiloted** (frozen/trimmed input, per the draft) — this exercises chunking and stepping load realistically, but not the interaction between a *real* client's `ControlInput` stream and a heavily-loaded chunked broadcast; test 7 already connects "a few real clients" alongside the synthetic load for exactly this reason, so this is a noted scope boundary, not a gap.
