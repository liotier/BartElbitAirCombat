# Project Roadmap: Derisking Sequence

## Status

Tentative, revisited at the start of each increment. This document exists to keep the increment sequence, its ordering rationale, and the standing design decisions in one place across a project that will span many implementation sessions and, eventually, contributors.

## Vision

A multiplayer WWII air combat game in the spirit of Battlebit Remastered: runs on modest hardware, pseudo-realistic (not simulator-grade) flight and combat, Linux-first, stylised art that keeps the tone light rather than tactical-larp-serious. JSBSim supplies the flight-model credibility Chuck Yeager's Air Combat had; Godot supplies the accessible, moderate-hardware footprint Battlebit has.

## Standing design decisions

These are carried forward across increments rather than re-decided each time. Revisit only if an increment's own review surfaces a concrete reason to.

- **Two-layer language split.** The simulation-facing layer (JSBSim integration, the GDExtension binding exposing it to the engine) is C++, matching JSBSim's native environment. The game layer above it (rules, UI, weapon/game-mode logic, entity orchestration) is **GDScript**, not C++ and not C#. Decided in increment 2 planning: GDScript is Godot's first-class, most-documented language, has no build step (hot-reload while the game runs, which matters for the gameplay-tuning code that gets rewritten dozens of times during playtesting), and is the lower-friction entry point for the kind of drive-by open-source contribution this project hopes to attract, since anyone arriving via Godot tutorials is already oriented in it. C#'s advantages (static typing, raw performance, a larger pool of developers who already know the language) matter less here than they first appear: the CPU-critical path stays in C++ regardless of the game-layer language, and most of the real difficulty in contributing to a project like this is architecture and domain understanding, not language syntax — a shallow, front-loaded cost regardless of which language is chosen.
- **CMake FetchContent, not submodules**, for C++ dependencies (JSBSim in increment 1; godot-cpp from increment 2 onward). Less to manage, and the caching behaviour means iteration doesn't refetch unchanged dependencies.
- **GPL-3.0-or-later**, with LGPL/MIT dependencies (JSBSim, godot-cpp, Godot itself) fetched at build time rather than vendored.
- **The working process**, established in increment 1 and intended to repeat for every increment: draft the increment's specification with the specifics pinned down explicitly (not left for the implementer to guess) → validate the draft's claims empirically wherever they can be checked by actually running something, rather than trusting documentation or plausible-sounding numbers → adversarial review of the draft, focused on whatever kind of wrongness that increment's domain is prone to (flight-dynamics judgment for increment 1; real-time-architecture and threading judgment for increment 2; netcode-specific failure modes — prediction, reconciliation, interest management — for the networking increments) → implement against the hardened spec → verify against the spec's own acceptance criteria → commit.

## The increment sequence

Increment 2 (Godot/real-time/rendering/input) and the final increment (weapons/damage) were fixed in increment 1's specification; weapons/damage was originally numbered 8, then 9 after increment 4 split in two, and is now 10, after bots was pulled out of what was increment 7 into its own increment (see below - the split increment 7 itself anticipated this: "with a split into its own increment if bot behaviour proves a bigger lift than expected"). Everything between is this document's proposal, provisional, and expected to shift as each increment's own review surfaces things the plan didn't anticipate — increment 2 planning and these two splits already did this three times.

1. **JSBSim standalone integration** — done. Validated that JSBSim produces stable, correct flight dynamics for a well-documented aircraft (c172x), driven purely programmatically, in isolation from rendering, networking, or game logic.
2. **Godot real-time integration** — done. Fixed-timestep JSBSim loop driven by Godot's own 120 Hz `_physics_process` (decoupled from render rate), a `FlightAircraft` GDExtension reusing increment 1's `FlightSession` unchanged, placeholder rendering, keyboard input in GDScript. Single aircraft, no networking. All four increment-1 scenarios pass through the Godot loop with matching physics; a real-time pacing test confirms 120 Hz against wall-clock.
3. **Client-server hello world** — done. A standalone, Godot-free `flight_server` owns the authoritative `FlightSession` (unchanged from increments 1-2), stepped at a wall-clock-paced 120 Hz; a new `netcore` library (ENet-only, no Godot/JSBSim dependency) defines the wire protocol's field-by-field little-endian serialization exactly once, shared unmodified by `flight_server`, the automated `flight_test_client` harness, and the Godot `NetworkClient`/`RemoteAircraft` GDExtension nodes. Server-authoritative (client sends inputs, server owns state); raw snapshot application, no prediction/interpolation (increment 4). Per the adversarial review's findings, automated tests assert transport fidelity (received snapshots compared field-by-field against the server's own sent log, not re-derived physics), a required input-path test (client input measurably changing server state), protocol behaviour (handshake, version rejection, clean disconnect), and resilience under latency/loss injected by a userspace UDP relay (`net_relay`) that impairs the real datagram stream — not an in-process queue, which would never exercise ENet's own reliability logic. Testing surfaced a real ENet bug (`enet_peer_disconnect()` immediately after a reliable send races that packet's delivery), fixed and documented in the spec's Appendix B alongside the pre-drafting validation findings (ENet/Godot coexistence, localhost RTT ~15 µs).
4. **Client-side prediction and server reconciliation** — done. Split off the "feel" half of what was originally one combined increment 4 ("multiplayer scaling and feel"); the "scaling" half is increment 5 below. A new `predictcore` library (Godot-free, depends on `flightcore`+`netcore`) defines `PredictedSession` - predict/buffer/reconcile/replay - shared unmodified by a new `PredictedAircraft` GDExtension node (subclasses `FlightAircraft`, confirmed workable) and `flight_test_client`'s `--mode prediction`. `GetVState()`/`SetVState()` is the rigid-body snapshot/rewind primitive (position, velocity, attitude, body rates); flight-control-system actuator/filter state is deliberately left unrewound. Adversarial review corrected two central draft assumptions before implementation: the actuator divergence is **not** self-correcting (a single reconciliation's residual grows without bound - what actually keeps it bounded is the continuous 30 Hz correction stream re-correcting the tiny inter-snapshot drift before it grows), and increment 3's "apply most recent input" server model desyncs under aggressive analog input plus loss regardless of prediction quality - fixed by the actual Quake/Source mechanism (redundant recent commands per packet, an ordered server-side command buffer), which `flight_server` now implements. The one place reconciliation could corrupt rather than merely fail to help - reconstructing a JSBSim rigid-body state from wire fields - was passed as a hard gate before implementation and reproduced as a real regression test (0.0 m / 0.0° / 0.0 m/s error). End-to-end validation against a live server confirmed sub-metre tracking on a clean link, under 100 ms latency, and under 20% loss with full-amplitude analog input, plus a forced-misprediction test with its required negative control (reconciliation disabled must - and does - leave the induced offset uncorrected).
5. **Multi-core server scaling** — done (`docs/increment-5-specification.md`, revision 3; review record in `docs/increment-5-specification-review.md`). Multiple concurrent aircraft/clients, server-side performance, and remote-entity interpolation (increment 4 has only one aircraft, so there was nothing else yet to interpolate). Pre-drafting validation re-measured increment 2's own `FlightSession::step()` figure — 57 µs mean was measured *inside a Godot `_physics_process`*, which does not apply to the Godot-free `flight_server`; standalone, steady-state per-aircraft cost is ~25–29 µs, giving a single-core mean-case ceiling of ~290–300 aircraft but a worst-case ceiling closer to 150–200 (worst-case tick time, not mean, is what a hard real-time budget actually needs to clear). **Multi-core parallelism of the independent per-aircraft physics remains a hard requirement, not an optimisation** — confirmed safe (zero divergence) with a hand-rolled lockstep-barrier thread pool across every configuration tested. A second, previously invisible ceiling turned out to matter more in practice than the CPU one: ENet's default MTU combined with today's per-aircraft wire field width means a single `StateSnapshot` broadcast silently stops being genuinely unreliable somewhere around 23-25 aircraft (ENet re-routes an oversized "unreliable" send through its reliable/fragmented path with no error or signal) — addressed in the spec by chunking the broadcast rather than by interest management, which is deferred until a concrete future trigger. The review caught a real gap in the draft's concurrency design: the barrier pattern its pre-drafting probes validated only proved worker threads stay in lockstep *with each other* over a *fixed* aircraft count, never a changing roster or a main thread doing real work between ticks (splicing in new clients, draining ENet's per-client command buffers) — exactly what the real server needs. The fix (a single barrier spanning workers *and* main, mutated-before-call/read-after-return) was verified directly against a roster that grows and shrinks mid-run, not just reasoned about. A further, user-prompted review pass asked whether the MTU finding meant reconsidering UDP snapshots altogether; the real alternative (ENet's own `UNRELIABLE_FRAGMENT` flag) was built and measured rather than assumed — it does stay genuinely unreliable at any size, but amplifies loss to `(1−p)^F` across F fragments with no per-fragment retransmit, which chunking avoids by keeping each chunk independently droppable at the raw per-packet rate; the same pass also caught and fixed a transport-decision reaffirmation gap and an interpolation-clock bug (timestamping by arrival rather than by server tick, which chunking's split arrival times would have let ordinary jitter read as motion). Implementation added a new Godot-free `interpcore` library (`RemoteEntityTracker`) that buffers each remote aircraft's received states on its own server-tick timeline and slerp-interpolates (or, past the newest sample, extrapolates via the exact constant-angular-velocity exponential map, bounded to a 300 ms cap) between them for rendering; `flight_server` gained a worker-pool-stepped roster of per-client `Aircraft` (async off-tick-path onboarding so a client's ~12 ms JSBSim init/trim never steals a tick from the barrier), player_id allocation separate from a test-only synthetic-stress range, chunked `StateSnapshot` broadcast, and a `PlayerLeft` message on disconnect; the Godot client now dynamically instances/frees a `RemoteAircraft` node per active remote player_id via a new GDScript spawner, reading interpolated pose through `PredictedAircraft`. End-to-end validation against a real server confirmed: three concurrent clients under an alternating-elevator cross-talk test produced altitude deltas with no cross-talk between clients (opposite-signed clients diverged in opposite directions, same-signed clients tracked within 0.01 m of each other); live remote-tracking held interpolated altitude within ~5 m of the raw broadcast value; capacity rejection and slot reuse both behaved correctly; and all four aircraft counts spanning the chunking boundary (16, 17, 30, 32) were observed at the exact expected count with zero duplicates by every connected client.
6. **Multi-airframe migration** — specification reviewed and revised (`docs/increment-6-specification.md`, revision 2; review record in `docs/increment-6-specification-review.md`), not yet implemented. Validates that the pipeline built around one hardcoded aircraft (c172x) generalises to others, using a small fleet of off-the-shelf JSBSim configs rather than a hand-authored one: **Camel** (Sopwith Camel, WWI rotary biplane) and **pa28** (Piper Cherokee) alongside the existing c172x baseline, all three confirmed - by actually loading and trimming each through this project's exact initialisation sequence, not merely checked for existing/licensed - to work with no code changes beyond parameterising the hardcoded aircraft name. Pre-drafting validation also surfaced why this fleet is three and not more: p51d's engine never starts (its custom autothrottle/mixture-control systems appear to fight `InitRunning()`, root cause not fully isolated), dr1 crashes on load (`Systems/pushback.xml` reads FlightGear-only properties JSBSim standalone never provides) and still fails to trim once that's patched, and L17 crashes on a different missing property (`fcs/flaps-pos-deg`) - each a distinct, aircraft-specific defect rather than a pattern indicting this project's own harness (confirmed by four *other* aircraft, including pa28, all trimming cleanly through the identical code path). Shelved rather than debugged further for now; revisit once there's a working proof of concept to demo. Also settles a standing control-model question the p51d finding raised directly: engine management (mixture, propeller pitch, startup sequencing) stays abstracted behind a single throttle lever, never exposed as separate player-facing controls - consistent with this project's own "pseudo-realistic, not simulator-grade" vision and with every increment's control scheme to date, and it structurally avoids reintroducing the exact class of bug p51d's engine-management systems caused.
7. **Bots** — specification reviewed and revised (`docs/increment-7-specification.md`, revision 2; review record in `docs/increment-7-specification-review.md`), with one open architecture decision for the owner (physics-less bot vs. bot with a local `FlightSession`); not yet implemented. The adversarial review's flight-behaviour probes found the draft's "simple time-based control schedule" keeps *no* airframe airborne — a physics-less bot can't self-determine trim (so the server must seed it, a wire change), keeping an aircraft in gentle maneuvers is a closed-loop attitude-control problem not an open-loop deflection schedule, and even a stabilised controller that flies c172x/pa28 solidly still spirals the Camel; so the maneuver logic is now a small autopilot gated on an automated airborne-endurance test, with the Camel gated (not assumed) for the bot fleet. A simple, headless control-and-perception version of the networked client (`flight_bot`), useful both for populating empty airspace around a server's spawn point and for automated testing. Connects like any other client (`ClientHello`/`ControlInput`/`StateSnapshot`, no local physics simulation - it trusts the server's own last-broadcast state for "where am I now") and feeds every other player's snapshot data into an `interp::RemoteEntityTracker`, the same "full airspace picture" a Godot client gets - not used for anything beyond simple maneuvers yet, but the perception plumbing future combat intelligence will need is in place from the start rather than retrofitted. For now, flies a simple repeating time-based pattern (climb, shallow bank, descend, level, repeat) with a bias back toward a safe envelope, nothing that reasons about other aircraft. `flight_server` gains `--bots N`: bots share the same player_id/capacity accounting as real clients (unlike `--stress-aircraft`, which deliberately sits outside capacity for load testing and never maneuvers), are displaced the moment a human needs the slot, and refill whenever a human disconnect drops the total back below N.
8. **Multiple aircraft types concurrently** — increment 6 validates that several airframes work *individually*; this is players actually choosing between them in the same running server (type-selection UX, mixed-type snapshots, whatever balance considerations that raises). Split from bots (formerly bundled together as increment 7) since bots are being built now, well ahead of this.
9. **Damage model foundations** — how battle damage manifests inside JSBSim's own state (engine damage → thrust, control-surface damage → authority, structural failure thresholds), deliberately separated from *how* damage gets applied over the network.
10. **Weapons, ballistics, hit detection, combat netcode** — guns, projectile/hitscan modelling suited to WWII gun velocities and ranges, lag-compensated hit registration tying into increment 9's damage model.

**Beyond increment 10**, this stops being a derisking sequence and becomes ordinary production: more aircraft, maps, game modes, UI, audio, matchmaking. Not part of this roadmap; it begins once the technical risk backbone above is retired.

## Explicitly deferred, unchanged from increment 1

Sound, music, GUI/menus beyond what an increment strictly needs to demonstrate itself, and persistence/save-load all remain out of scope until a later increment names them explicitly.

## Scenery ideas, not yet scheduled

Two rendering/scenery ideas worth keeping on record for whenever "maps" (see "Beyond increment 10" above) actually gets scoped as real work - not acted on now, and not part of any numbered increment above:

- **Giant simple-shape landmarks** as an interim visual/navigational reference before real terrain exists (eventually, Copernicus/SRTM-derived elevation plus OpenStreetMap-derived buildings) - kilometre-scale primitives (a sphere, a cube) placed in the world so players have something to orient by ("fly around the sphere, then head towards the cube") against what is currently an entirely flat, featureless ground plane.
- **"Micro-machines" scale exaggeration**: aircraft stay at true 1:1 scale, but terrain relief (the DEM) is scaled up for sharper, more dramatic elevation than the real data would give, and buildings scaled up a further 10x on top of that - deliberately unrealistic, in the same spirit as FPS games' gratuitous crate-strewn levels, purely for gameplay/visual interest rather than geographic accuracy.
